# Local runner enrollment and health contract

Recorded 2026-10-14; updated 2026-10-20 (Asia/Kolkata). [Findings index](README.md)

## First V0.3 increment: verified locally

This records the first increment's boundary. The subsequent [compute-control contract](runner-compute-controls.md) extends its fixed-false dispatch approval with admin approval and explicit use grants; consult the [October 24 checkpoint](../progress/2026-10-24-01-compute-controls.md) for accepted implementation, verification, and limits.

An explicit team admin issues a ten-minute enrollment code for a named local runner. The foreground runner exchanges that code for its own identity and sends authenticated heartbeats every 15 seconds. Team members can inspect non-secret registration/health metadata; only team admins can revoke a pending or enrolled runner. This increment is a health connection, with no dispatch approval, grants, capacity claims, jobs, repository commands, containers, or model calls. V0.3 remains incomplete.

The contract below is implemented in shared runner schemas, migration 006, the API runner service/routes, `apps/runner`, and the Compute page. The [October 20 checkpoint](../progress/2026-10-20-01-runner-enrollment.md) records passed automated and browser/foreground-runner acceptance, recovery runs, cleanup, and limits. Full V0.3 compute controls remain separate work.

- Human endpoints: `GET /api/teams/:teamId/runners?cursor=UUID` (50 records per page), `POST /api/teams/:teamId/runner-enrollments`, and `POST /api/teams/:teamId/runners/:runnerId/revoke`. Existing cookies and current explicit team membership apply. Issue/revoke require `admin` under held identity/membership locks, beyond the existing developer catalog permission. Organization ownership alone does not grant team access.
- Machine endpoints: `POST /api/runner/enroll` and `POST /api/runner/heartbeat`. They accept only their respective enrollment/runner bearer credentials, never a human cookie as authority. Host, exact Origin, and JSON requirements stay intact. The CLI explicitly sends an approved local Origin; its API/Origin URLs must be loopback HTTP without credentials, query, fragment, or non-root path, and redirects are refused.
- Credentials use distinct `ark_enroll_UUID_64hex` and `ark_runner_UUID_64hex` realms. Browser Web Crypto generates the enrollment code, and the runner generates its credential before exchange. Both use 32 random bytes. Only full-token SHA-256 hashes are stored. The runner UUID embedded in each token must match its record. No secret enters an audit, log, URL, browser storage, command argument, or checked-in file.
- The browser retains one issue request's UUID/name/code in memory across an uncertain response. Identical requests replay the same record; changed fields under the same ID conflict. Only a confirmed successful issue exposes the code, masked by default. Team change/logout/unmount clears the code; a reload cannot recover it. Pending codes can be invalidated by revoking their record.
- Enrollment locks and revalidates the issuing user's active organization membership, user status, and explicit team-admin membership before locking the runner. Expiry is checked using database wall-clock time after lock acquisition. Consumption, credential hash, enrollment timestamp, lifecycle counter, and safe audit commit atomically. Identical code/credential exchange may replay within the original expiry; a different credential cannot consume an already-used code. A lost response can be reconciled with a heartbeat using the locally generated credential/UUID. Concurrent consumption produces one credential identity and one audit.
- An enrolled runner is a team service identity, independent of the issuer's subsequent login/logout or role change. Unused codes lose authority if the issuer loses admin access. Revocation explicitly disables the enrolled runner; it is irreversible. Heartbeats and revoke lock/recheck the same runner row. Human lifecycle counters change on enrollment/revoke, never on heartbeats. A stale active revoke conflicts; repeated revoke of an already-revoked record is an authorized no-op.
- Heartbeats accept an empty strict JSON body and use server receipt time, not client time. Health is `unknown` before the first heartbeat or after revocation, `online` while a heartbeat is at most 60 seconds old, and `offline` otherwise. Reads derive health without a scheduled job. Last-seen timestamps remain visible after revocation; revoked does not claim the host itself is offline. Health never grants execution authority; `dispatchApproved` remains false.
- Migration 006 adds mutable team-scoped runner/enrollment state outside the immutable catalog. Composite team/organization and issuer membership foreign keys preserve ownership. Names are labels and may repeat; UUIDs identify records. Runtime grants allow only SELECT/INSERT/UPDATE on this table, with no deletion. Prior migrations remain unchanged.
- Runner credentials stay in foreground-process memory. The code is entered through hidden terminal input or a noninteractive stdin pipe, never a flag/environment value. Restarting this process requires new enrollment; protected persistent credential storage is deferred explicitly. API restarts can reconnect the same running process. Requests have finite timeouts, retries use bounded backoff, authentication rejection stops the process, and shutdown aborts pending requests/timers. Logs contain status only.

## Acceptance boundary

Strict schemas/realms and token-to-ID pairing; all roles/team/session boundaries; issuer revocation/demotion/disable before exchange; expired/used/revoked codes; identical replay and response-loss recovery; concurrent consumption and rollback; runner/cookie realm separation; heartbeat/revoke ordering; expiry after a blocked lock; heartbeat timestamps and unchanged lifecycle counters; derived offline state; API restart persistence; restricted runtime privileges; safe audit/log/error bodies; CLI URL/redirect/timeout/retry/shutdown behavior; UI secret handling, uncertain requests, stale/offline/team-change recovery; and actual browser plus foreground-runner issue/enroll/online/offline/revoke checks. Existing catalog/identity suites remain regressions. Record actual checks and limitations before calling this increment verified.

After this boundary is accepted, define dispatch approval and explicit compute grants as the next bounded contract. A successful heartbeat must continue to provide no job authority. Protected persistent credential storage, compatibility/capacity claims, and execution each need their own decisions and evidence.

## UI reference lock

Use the existing Ark console as the primary target: compact system typography, neutral panels/borders, restrained purple actions, native labels, readable identifiers, and a narrow content column. Separate registration, last heartbeat, and unavailable dispatch approval instead of an aggregate readiness badge. Issue code -> connect foreground runner -> refresh health -> confirmed revoke is the bounded journey. Mask the code, preserve recoverable failures, and do not invent execution controls. Refero/craft research for concrete form/list states is recorded by the implementation review; no imagery or redesign is required.
