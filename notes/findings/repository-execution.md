# V0.5 repository preparation and command contract

Recorded 2026-10-25 (Asia/Kolkata). [Findings](README.md) · [Progress](../progress/2026-10-25-02-repository-planning.md)

## Boundary and first slice

V0.4 remains the accepted `stub.v1` protocol. V0.5 will add a separately versioned `repository.v1` execution mode for a trusted repository and one explicitly selected saved Workspace action (`install`, `test`, `lint`, or `build`) per run. Selecting one action never implicitly runs another. Agent instructions and capabilities stay inert until their later runtime milestone. No model, credential, push, PR, or deployment work belongs to this contract.

The first implemented slice is a **pure shared command-plan compiler**. It validates and copies an immutable Workspace reference/definition, the selected action, a declared full commit identity, and a declared image digest into a bounded plan. Its status is `planned_unverified`. It performs no lookup, authorization, fetch, image inspection, checkout, command, or evidence collection. A valid plan establishes syntax and intent; source existence, source/ref correspondence, image availability/trust, and real path containment require later checks.

Current backend slices also store immutable saved plans and separately admit them for preparation under the [October 26 control contract](repository-execution-control.md). Admission reauthorizes compute and establishes shared runner ownership. It creates standalone one-action repository work because current Flow stages describe Agents; a future Flow command stage must explicitly match the Workspace pin. There is no repository worker adapter, command-start/completion/release endpoint, or execution UI yet. The [checkpoint](../progress/2026-10-26-02-repository-execution-control.md) records actual verification and limits.

## Source, image, and command identity

- Preserve the selected Workspace resource/version IDs and its repository URL, requested `sourceRef`, image reference, and relative directory. A branch/tag is recipe context, not an immutable source identity. Initially support an explicit 40-hex SHA-1 commit OID; abbreviated OIDs, refs, and other object formats are unsupported as the execution commit. If the Workspace already names a full 40-hex commit, require that same commit. The future preparation receipt separately records the commit actually obtained and verifies exact equality. A moved ref cannot silently substitute a commit.
- Require a digest-qualified image reference, `repository@sha256:64-hex`, using the same repository spelling as the saved Workspace image. If that Workspace already pins a digest, require the identical digest. Resolving tags, inspecting local images, and checking the operator's digest allowlist happen later. A digest names content; it does not establish trust.
- Copy the selected saved command **verbatim** for `/bin/sh -c` inside the command container. Reject an empty/whitespace-only action. Shell syntax is intentional configuration, never a host shell command or an argv string to split on spaces. Lexically validate the relative working directory now; future preparation must resolve it inside `/workspace/repository` and reject missing directories or symlink escape.
- The server will compile plans from separately authorized immutable Workspace/Flow snapshots. It must not accept replacement client commands, policy, limits, host paths, mount options, or image repositories. Later catalog changes do not modify a saved execution plan. Persist its versioned canonical form and SHA-256 digest before dispatch; receipts bind to that exact plan.

## Controlled preparation and execution

The runner operator opts in to repository work separately from `--stub-sessions`. A future operator policy admits exact repository hosts and trusted locally available Linux image digests. The initial public-HTTPS transport supplies no credentials, prompts, inherited credential helpers, recursive submodules, LFS filters, hooks, user Git configuration, or templates. Git operations use fixed executables and argument arrays inside a controlled preparation container, with protocol/redirect/environment restrictions. Private-repository authentication and dependency-network policy require later contracts.

Use a dedicated named Docker workspace volume and exact owned container identities, derived only from session/lease UUIDs and generation. Never mount the user's checkout, home, Docker socket, database volume, or credential/configuration directories. Persist a secret-free ownership manifest before resource creation so response loss reconciles the same named resources and ownership labels. An absent or mismatched manifest is not permission to adopt/remove a resource. Never use global prune or broad volume cleanup.

The `docker-linux-offline.v1` command policy requires Linux, non-root UID/GID 1000, no network or published ports, private process namespace, all capabilities dropped, no privilege escalation, read-only root filesystem, and only the owned workspace plus bounded temporary storage writable. Preparation uses its own trusted transport environment; repository commands use the offline policy. The initial fixed budgets are preparation 120 seconds, selected command 300 seconds, cleanup 30 seconds, whole repository run 900 seconds, two CPUs, 1024 MiB memory, 1024 MiB workspace storage, 128 PIDs, 64 MiB temporary storage, and 64 KiB retained output per channel. The run deadline reserves cleanup time. These are policy limits, not values a plan caller may increase. A future adapter must fail closed if a required limit cannot be enforced. Volume/storage quota enforcement needs explicit adapter evidence before real-work acceptance; these declarations do not prove isolation.

An offline `install` action can use dependencies already available in the approved environment. Planning supplies no network access, image pull, implicit dependency install, or provisioning. A controlled fixture can establish real execution without making general dependency/network support a prerequisite.

## Durable authority, leases, and recovery

Extend storage through additive migrations; preserve applied migrations and old rows. Migration 009 stores immutable plans; migration 010 adds standalone repository executions, a runtime discriminator in shared leases, and append-only control receipts. Preparation/process/cleanup reports remain future work. Existing `stub.v1` requests, responses, stage validation, and `not_evaluated` quality retain their meaning. Stub-only runners never claim repository work. Current starter/team/organization eligibility, explicit grant, runner approval, protocol compatibility, and capacity are rechecked at admission, claim, and work control; protocol declaration is not verified sandbox capability.

Persist ownership before preparation. Keep the existing actor identity -> runner -> session -> lease lock order and exclusive active-or-uncertain reservation. Add an idempotent work-control/renewal operation for commands lasting beyond the 45-second lease: one serialized controller or a separate lease sequence avoids racing stage expected revisions. Registration heartbeats remain separate. Renewal checks fresh authority, cancellation, the server deadline, and the whole-run deadline; renewals cannot extend a run indefinitely. The local controller uses a conservative monotonic deadline and stops work when authority becomes uncertain.

Cancellation, timeout, revocation/permission loss, transport exhaustion, or shutdown requests termination of the exact owned work. Aborting the Docker CLI is not stopped-process evidence. Graceful stop may escalate within a fixed cleanup budget, followed by inspection/wait proving the owned container exited and no owned process remains. Record cleanup evidence before acknowledging stop and releasing ownership. Unknown daemon/container state retains uncertainty and its reservation. Process restart discovers owned orphans from the manifest without storing machine credentials or lease tokens on disk. The V0.4 stub-only admin `confirmedStopped: true` shortcut must never release repository ownership by itself; repository recovery requires verified cleanup evidence.

## Reports and quality

Each append-only report binds session/lease/generation, plan digest, Workspace version, declared and observed commit/image identities, action, exact command, start/end times, exit code/signal, timeout/cancellation, output checksums/truncation, and cleanup outcome. Store bounded protected output through authorized team/session access; stdout, prose, and exit zero alone do not establish quality.

The bounded [preparation receipt journal](repository-preparation-receipts.md) implements the first observation boundary independently of future process reports: exact lease/plan/resource binding, immutable token-free storage/replay, bounded diagnostics, and current member reads. Its evidence is always `runner_reported_unverified` and grants no work or release authority. Full process/cleanup reports and real adapter observations remain later work.

Keep process status separate from test/check verdict. A successful command may still have `not_evaluated` quality. Missing tests, missing/unsupported/malformed reports, zero discovered/executed tests, entirely skipped tests, uncertain cleanup, and incomplete evidence are **non-pass** outcomes. Initial positive test evidence will require a bounded structured report adapter (starting with JUnit XML), validated counts and file containment, no external entity resolution, and an immutable report checksum. The command must explicitly emit that format; do not append guessed framework flags or infer counts from console text. An `install`/`lint`/`build` command cannot establish tests passed. Bind checks to the inspected source/worktree state so subsequent changes invalidate their freshness without deleting historical reports. This first planning slice emits no report or quality verdict.

## Acceptance and sequence

### Saved-plan API slice (original contract, implemented)

The saved-plan backend stores **non-dispatchable immutable plans**, independently of runners and execution sessions. This separates reusable declared intent from execution admission while the repository adapter protocol is incomplete. No runner enrollment, grant, capacity reservation, job, lease, or work event is required or created by planning. Separate execution admission reauthorizes compute, binds the exact plan and Workspace pin, and establishes ownership intent before effects, as detailed in the control contract.

Human-cookie endpoints under `/api/teams/:teamId`:

| Method/path                         | Request/result                                                                                                                              |
| ----------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------- |
| `POST /repository-plan-previews`    | `{workspace:{resourceId,versionId},selection:{action,commitOid,imageDigest}}` -> `{plan,planDigest}`; current team members, no writes/audit |
| `POST /repository-plans`            | Preview fields plus client UUID `id` -> `{repositoryPlan}`; current admin/developer; 201 new/200 identical replay                           |
| `GET /repository-plans?cursor=UUID` | Current team members; 50 metadata summaries and `nextCursor`, UUID keyset order; no full commands/definitions in list rows                  |
| `GET /repository-plans/:planId`     | Current team members; complete saved plan/provenance/digest                                                                                 |

Only these fields are accepted; definitions, commands, policy, limits, compiled plans, and execution flags cannot be supplied by callers. Preview/new Save resolve an active supported Workspace version from the current explicit team under identity/membership and owning-resource SHARE locks. Any selected supported historical version of an active Workspace is valid. An archived, cross-team, wrong-kind, unsupported, missing, or mismatched version receives a generic dependency error. Preview is a read-authorized operation; Save requires the same admin/developer write role as catalog configuration. Preserve exact Host/Origin/JSON requirements and the normal request-size cap.

Migration 009 adds `repository_plans` with tenant/creator/Workspace provenance, normalized request, compiled selected configuration, versioned plan digest, and created time. Composite foreign keys bind the resource kind/team/organization and resource/version pair. Existing immutable catalog versions retain the complete original Workspace definition; the saved plan copies only the selected execution configuration it needs. Runtime access is SELECT/INSERT only; an immutable-row trigger also rejects UPDATE/DELETE. Applied migrations remain unchanged. Migration 010 keeps the existing Flow-session schema/public protocol and adds repository ownership to the shared lease table separately.

The v1 digest is SHA-256 of UTF-8 `serializeRepositoryCommandPlan(plan)`: strict plan-schema parsing reconstructs the fixed v1 field order before JSON serialization, including nested fields. Key order in incoming JSON or PostgreSQL JSONB must not affect it. Limits/policy/version-1 semantics are frozen; future semantic changes require a new supported plan/policy version.

Save atomically writes the plan and one safe audit, validates the concrete response, and rechecks browser-session expiry after blocking work. After identity authorization, a transaction advisory lock serializes the client UUID in the `ark:repository-plan` namespace before current catalog lookup. An identical waiter therefore reads the winner's saved record even if the Workspace was archived in between. Identical ID replay compares normalized request plus creator/team/organization and returns the saved compiled plan without resolving today's catalog or adding audit. A changed request/creator/tenant returns generic `ID_CONFLICT`. Defensive `INSERT ... ON CONFLICT DO NOTHING` handling re-reads and applies the same replay checks; it must not manufacture a conflict for an identical request. A losing insert can wait, so expiry must be rechecked after that wait even when the insertion succeeds after another transaction rolls back. Reads remain separately authorized after catalog archival or later creator-role changes. A saved plan remains `planned_unverified` throughout.

Saved-plan acceptance covers no-write preview, all role/team/org/session boundaries, exact saved versions and selected commands, canonical digest, immutable snapshots after edits/archive, idempotency/concurrent creates and restart reads, expiry/revocation around lock waits, audit/response rollback, bounded summary pagination, runtime privileges/immutability, strict HTTP bodies/queries, and no execution/lease/runner side effects. Separate admission/preparation control is now verified locally; its own acceptance and remaining receipt/adapter/UI work are recorded in the control contract.

1. **Shared planning (implemented):** exact identities, digest matching, strict policy/limits, verbatim selected commands, safe lexical directories, deterministic copied plans, clear unverified status; focused pure tests and shared build.
2. **Storage and API (partial):** immutable saved plans plus standalone execution admission, shared ownership, current authority, preparation controls/cancellation, and expiry are verified locally. Bound preparation/process/cleanup receipts and trusted observations must precede command start, completion, release, and real adapters.
3. **Runner adapters:** real exact-source preparation, approved image observation, resource manifests, containment, enforceable budgets, process supervision and verified cleanup; controlled disposable repositories/containers and failure/response-loss checks.
4. **Session UI and acceptance:** explicit mode/action/source/image choice, separate process/quality/preparation/cleanup reports, honest no-tests outcomes, reload/SSE/cancellation/recovery, desktop/mobile checks, exact fixture/service/resource cleanup. V0.5 remains incomplete until this evidence exists.
