## Purpose and sequence

Continue from `ea85cfe` with create, list, read, edit, and reload for team-owned Agent definitions. Keep the existing Workspace and identity behavior. The increment follows shared contracts, migration 003, authorized backend operations, then the frontend. It adds no dependencies or model calls and does not complete V0.2.

The shared definition includes instructions, a `stub` runtime choice, nullable model preference, and requested capabilities. The stub choice is configuration for later execution work; no runner is implemented. Empty capability preferences grant nothing. Future authorization must independently resolve effective permissions.

## Implementation and trade-offs

- Contracts: `packages/contracts/src/agents.ts`; shared PostgreSQL-safe text validation in `catalog-text.ts`, reused without changing Workspace validation.
- Database: `003_agents.sql` and the migration registry expand the allowed resource kinds. Applied migrations 001/002 and runtime privileges stay unchanged.
- API: explicit Agent routes/service use shared catalog transactions, authorization locks, revision checks, immutable snapshots, safe creation replay, and audits without definition content.
- Web: feature-owned fields and adapters with shared list loading, draft recovery, and navigation protection. All supported fields round-trip; unknown stored schemas are read-only.
- Tests: Agent contract/integration/DOM checks plus existing Workspace and identity regressions. The identity migration assertion now expects three migrations.
- Notes: [Agent guide](../learning/08-agents.md), [Agent findings](../findings/agents.md), the architecture tree, roadmap, and corrected older snapshot pages.

Sharing the versioning/recovery mechanisms is justified by two real catalog kinds. Domain field layouts and HTTP contracts remain concrete; no generic form generator, persistence framework, or speculative execution abstraction is introduced. Agent mutation bodies allow 128 KiB to fit the supported maximum escaped instruction content, while Workspace/identity limits remain unchanged.

## Browser walkthrough

Playwright CLI with Chrome used Vite on 5184 and the disposable API on 3002. A fictional owner/team and catalog records lived only in a generated `ark_test` schema.

1. Setup reached the authenticated shell; Agents navigation and the empty catalog worked. New Agents had no capabilities selected and an empty model preference.
2. Empty creation showed validation errors and focused Name.
3. Creating an Agent saved revision 1 and navigated to its persistent URL. Reload assertions matched all fields, including multiline description/instructions, surrounding whitespace, emoji, model preference, stub choice, and all capability selections.
4. A second tab saved revision 2. The older editor received an explicit conflict and retained its draft. Confirmed Load latest retrieved the winning instruction and revision.
5. An offline save failed without losing its draft. Restoring the network and manually saving succeeded as revision 3.
6. Navigating from a dirty Agent to Workspaces showed the Agent-specific leave prompt and focused Stay here. Staying preserved the draft; returning the field to its saved value cleared the dirty state.
7. Desktop 1440px and mobile 390px screenshots were inspected. Mobile content width equaled viewport width (390px); fields, capabilities, helper text, and Save remained readable. Local images are ignored under `output/playwright/agent-*.png`.
8. A Workspace with the same name as the Agent was created through the refactored form. Reload assertions matched all 11 controls, including empty and whitespace-bearing action strings. An immediate scripted reload first met the pending navigation's before-unload guard; after confirming and allowing the page to settle, every saved field matched.

Console errors corresponded to the deliberately induced 409 and offline request; no unexpected application error was observed. Both QA servers and the browser were stopped. A follow-up query confirmed the identified browser schema was removed, and both QA ports were no longer listening. Development records and Docker volumes were preserved.

Browser verification is a walkthrough, not a committed end-to-end suite or complete accessibility audit. Role downgrade, unknown schemas, delayed team reads, capability clearing, and uncertain creation recovery have DOM/API coverage; not every case was repeated in Chrome. No real model, repository execution, cloud provisioning, or deployment was attempted.
