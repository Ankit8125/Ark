## Purpose and contract

Continue from `5048b079a35db27f57f4d8331f0ae344cd2c342a`, the published Agent catalog checkpoint. Add team-owned Flow configuration that pins one Workspace version and an Agent version for each ordered stage. This increment follows shared schemas, migration 004, backend operations, and the frontend; no new library, model call, or execution service is required.

The definition has named text/JSON inputs, 1–20 ordered agent stages, and named final outputs. Each stage has 1–8 input bindings and output declarations; the Flow also has 1–8 inputs and final outputs. Stage inputs consume a Flow input or an earlier stage's output of the same type. Final outputs select stage outputs. Stable stage identities preserve references during reordering. Missing sources, forward references, duplicate names/identities, and type mismatches cannot be saved.

Resource/version pairs must belong to the requested kind and the Flow's team/organization. Saving checks the actual pinned snapshot inside the authorized transaction. Updating a Workspace or Agent must never silently advance an existing Flow's pin. Historical version reads provide the selected snapshot without introducing a history/restore UI.

## Work in progress

The shared contracts and API compile; the initial ten Flow contract tests pass. Migration 004 was applied with `pnpm.cmd db:prepare`, preserving the existing database and volume. A read-only verification connected as `ark_app` to `ark_dev` and found four migrations, zero users, and zero catalog resources. Docker reported PostgreSQL healthy on loopback port 5434.

Independent backend review caught a lock-coverage edge case: a resource that became newly visible between the dependency lock and lookup statements could otherwise be resolved without a held lock. The validator now requires every reference to appear in the returned locked-ID set before looking up immutable snapshots. No transfer endpoint exists today; the correction keeps the transaction's locking claim accurate.
